# P4/P5 — воспроизводимая оценка активности

Дата: 6 ноября 2026 года. Дополнение к плану v2. Новые модели работают только в shadow;
на старые сигналы, отбор AI и правила отправки новых уведомлений не влияют.

## P4: история и модели

1. Сохранять версии спецификаций в агрегатах. Не смешивать площадки, каналы,
   тип агрегации и спецификации. Минуты без происхождения, с неизвестными единицами,
   пропусками, конфликтами или provisional исключать. Реальные нули сохранять.
2. Сравнивать отдельно число исполнений и оборот в валюте своей площадки.
   Использовать медиану последних 14 последовательных минут, эмпирический квантиль,
   MAD от log(1+x), односторонний CUSUM. Масштаб MAD = 1.4826 × median(|x−median(x)|).
   CUSUM: S=max(0,S+z−k); k=0.5, h=5 — исследовательские настройки.
3. Версионировать параметры, состав базы, значения, ревизии и хеши исходных окон.
   Target не включать в базу. Будущие минуты не использовать.
4. Для офлайн-сравнения делить запрошенный период хронологически 70/30.
   Базу фиксировать перед проверкой. Считать кандидатов до cooldown, эпизоды,
   подавления, календарную частоту и покрытие. Делить проверочный период ещё на три
   последовательных участка для оценки изменения частоты.
5. Сохранять входной снимок, его checksum и отчёт; обеспечивать повтор без сети.
6. После P3 накопить репрезентативную историю; проверить сезонность и режимы на
   нескольких неделях. Выбрать пороги до отдельной итоговой проверки. Ни один
   программный флаг достаточности не заменяет эту приёмку.

Текущие ограничения для исследовательской базы: горизонт 7 суток, покрытие ≥99%,
минимум 2000 наблюдений и 20 наблюдений в хвосте q99. При требовании покрытия
за семь суток фактически потребуется около 9980 пригодных минут на источник.
Это инженерные ограничения, не доказательство независимости наблюдений или
достаточности для сезонной модели. Нулевые MAD/медиана дают явное состояние.

## P5: интеграция

1. Read-only адаптер читает закрытые UTC-минуты по общему времени двух площадок.
2. Теневой расчёт охватывает контрольные BTC/XRP и текущие подробные инструменты
   attention. В журнале отдельно сохраняются профили и оценки; повтор не создаёт
   дубликат. История подробных сделок инструментов вне attention не считается наблюдаемой.
3. В snapshot/UI/Telegram передавать ID оценки, baseline и фактический размер базы.
   До проверки порогов activity остаётся threshold_not_calibrated. AI не получает
   эти оценки как новое подтверждение; новые торговые уведомления не создаются.
4. Карточку связывать с оценками. При позднем изменении окна или составляющей базы
   создавать новую версию оценки с correction_of. Автоматическая коррекция ограничена
   последними 24 часами, чтение — восемью сутками (семь суток базы + сутки коррекций).
   Более старые пересмотры требуют офлайн-исследования; автоматическое обновление
   старых карточек за этим горизонтом не заявляется.
5. В исправленной карточке явно помечать исходный межбиржевой блок и показывать
   новые количество исполнений/качество/версию. Использовать существующий message_id;
   не отправлять новое сообщение задним числом. Pending переживает рестарт;
   failed остаётся в pulse_card_edits, без бесконечных повторов.
6. Модульные и HTTP-проверки использовать с подменённой доставкой. Реальную
   Telegram-приёмку выполнить в согласованном тестовом канале до P6.

## Запуск и откат

Единая точка запуска проекта сохранена: start.ps1 или start.sh. Дополнительный
микросервис не требуется: исследование — отдельная команда, shadow — часть screener.
Новая зависимость не добавлена. PULSE_SHADOW=0 отключает shadow и сохранение новых
оценок, оставляя сбор и описательный контекст. Новые сигналы программно не допускаются.

Исследование через read-only API из корня проекта:

```powershell
uv run python -m hyperdata_terminal.market_pulse.research --days 14 --output work/p4-study
uv run python -m hyperdata_terminal.market_pulse.research --input work/p4-study/input.json --output work/p4-replay
```

Выход: input.json, report.json, report.md. По умолчанию API http://127.0.0.1:8431.
Старые окна не получают фиктивную спецификацию задним числом. Это может временно
оставить базу пустой, хотя общий журнал сделок уже содержит данные.

## Границы готовности

Программный контур исследования и shadow реализован. P4 не считается статистически
принятым до накопления/проверки истории. Реальная приёмка P5 выполнена 6 ноября:
одна rich-карточка в чате из .env, редактирование, успешный no-op и обновление того же
message_id после запуска нового процесса. Неопределённый исход отправки не повторяется
автоматически; для ответов 429 сохраняется retry_after, планировщик такого повтора
пока не реализован.

Для ограничения ресурсов исследовательская база фиксируется на границе часа
(hourly_frozen.v1); target и будущие окна в неё не попадают. Состав базы сохраняется
один раз на профиль. Исторические исправления инвалидируют соответствующий профиль;
очередь пересчётов сохраняется и обрабатывается ограниченными порциями.

Широкий слой свечных сводок Hyperliquid хранится отдельно 30 суток и не складывается
с подробными исполнениями. Медиана 14 предшествующих последовательных минут помогает
выбирать инструменты attention; это локальная эвристика отбора, а не сезонная норма
или оценка редкости. После reconnect, пропусков или недостаточно свежих обновлений —
прогрев. Для каждого пригодного бара требуется обновление в последних 10 секундах
минуты или не позднее 15 секунд после неё. Такое условие консервативно: тихие
инструменты могут не иметь пригодной базы. Завершённость биржевых данных не доказана.
Проверка последних ревизий агрегатов не равна воспроизведению потока «что было
известно в тот момент»: для последнего нужен отдельный журнал всех ревизий/времени
поступления. В исследовательском отчёте это ограничение сохранено явно.
Не заявляется сезонная норма, прибыльность или две независимые вероятности.

Далее: P3 → несколько недель истории → сравнение/выбор порогов → независимая
проверка и Telegram-приёмка → решение по P6. Следить за размером journal: профили
сохраняют состав базы для воспроизводимости; ресурсная приёмка остаётся частью P3.

Источники формул: [NIST CUSUM](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc323.htm),
[GSL MAD](https://www.gnu.org/software/gsl/doc/html/movstat.html).
