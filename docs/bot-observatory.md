# Наблюдатели сигналов: контракт и протокол

**Статус:** реализованы `flow.continuation` (строки скринера) и семь наблюдателей по событиям
(этап 4 в docs/multi-bot-plan.md): `tape.reading`, `formation.hold` / `formation.break` (v2),
`liquidation.continuation` / `liquidation.exhaustion` (v2), `attention.relative_move` (v3),
`whale.follow` (v4). События приходят через `BotObservatory.record` (карточки, ликвидации, позиции) или
из сравнения плана отбора между проходами; эпизоды, cooldown, контроли и исходы те же. AI-наблюдатели
ждут включения AI; `funding.contrarian` отложен.

Это не торговые боты. У наблюдателя нет баланса, позиции, плеча и PnL.
Он записывает, что было видно в момент решения, и считает, что произошло
через 1, 5 и 15 минут. Результат — движение цены в базисных пунктах, а не
доходность счёта.

## Зафиксированные решения

| Вопрос | Решение |
|---|---|
| Цель | Измерять сигналы, а не управлять капиталом |
| Единица | Тип анализа — бот; сила — разрез статистики |
| Сила | Своя шкала 0–4 у каждого типа; 0 = нет данных |
| Режим | `directional` для направленных, `absolute` для отбора/контекста |
| Горизонты | 1 / 5 / 15 мин; основной — 5 мин |
| Вход | Mark price + 1 секунда, допуск 5 секунд |
| Выход | Mark price; если нет — закрытие свечи; иначе `unscored` |
| Контроль | 5 одновременных неактивных инструментов в том же bucket NATR |
| Эпизод | Один эпизод — одно наблюдение, повторные срабатывания не считаются |
| Вывод | `<30` — мало данных, `30–99` — предварительно, `≥100` — достаточно |
| Ошибка | Block bootstrap по 15-мин блокам; Wilson для hit rate |
| Множественные сравнения | 9 главных тестов, BH q=0.1, версии контрактов |
| Хранение | Внутри screener, существующий SQLite-журнал |
| Интерфейс | Telegram: `/bots` и `/bot <id>` |
| История | Live и replay — два независимых трека; в общую статистику не смешиваются |

|---|---|---|---|---|

| `attention.relative_move` v3 | absolute | инструмент получил детальный слот (аномалия или мувер) после 10 минут без него | Движение выше контролей вне отбора | реализован |

| `formation.hold` v2 | directional | цена подошла к значимому уровню (бот плотностей) | От спроса вверх, от предложения вниз | реализован |

| `liquidation.exhaustion` v2 | directional | тот же триггер, обратная гипотеза | После каскада разворот | реализован |
| `whale.follow` v4 | directional | открытая или увеличенная позиция ≥ $250k на Hyperliquid, ≥ 1 средней минуты объёма HL + Binance | Цена идёт в сторону позиции | реализован |
| `funding.contrarian` | directional | funding/basis/L-S выше порога | Перекос возвращается к норме | отложен |

`whale.fade` сознательно не включён: это отдельная гипотеза, для неё нужен
отдельный повод, а не перебор вариантов.

Для `flow.continuation` дополнительно исключается широкий спред: иначе
слабая группа смешивалась бы с плохим исполнением, а не только с силой
сигнала.

## Контракт бота

Контракт объявляется до сбора данных:

```json
{
  "id": "flow.continuation",
  "version": 2,
  "mode": "directional",
  "trigger": "flow_continuation",
  "strength": "flow_rank_0_4",
  "hypothesis": "Сильный поток (rank 3–4) продолжается лучше слабого (rank 1–2)",
  "primary_horizon_s": 300,
  "cooldown_s": 300,
  "control": "random_scout_vol_5",
  "primary_test": "mean signed bps, rank 3-4 > rank 1-2",
  "window": "5m"
}
```

Любое изменение порога, cooldown, шкалы силы, горизонта или политики
контроля требует **новой версии**. `bot_versions` хранит хеш контракта;
попытка переиспользовать ту же версию с другим содержимым завершается
ошибкой, а не молчаливым смешиванием старой и новой статистики.

## Эпизод

Состояние хранится в `bot_state` по ключу `(bot_id, version, symbol, window)`.

- Условие стало истинным → создаётся эпизод и наблюдение.
- Условие остаётся истинным → обновляется `last_seen`, новых наблюдений нет.
- Направление изменилось → новый эпизод, но не раньше 60 секунд жизни
  текущего: частые развороты не создают наблюдений.
- Условие стало ложным → после 15 секунд без подтверждения `direction=0`,
  `last_seen` фиксирует конец. Один пропущенный скан не обрывает эпизод.
- Повторный вход после паузы — не раньше `cooldown_s`.
- Пропажа инструмента из обзора → состояние устаревает; при возврате после
  `2 × window` создаётся новый эпизод.

Идентификаторы детерминированы:

```
episode_id = sha1(bot_id, version, symbol, window, direction, floor(now / window))
```

Поэтому рестарт screener не создаёт дубль. Уникальный индекс
`(bot_id, version, trigger_event_id)` — последняя защита.

## Измерение

Для каждого наблюдения:

1. `entry_due_at = decided_at + 1s`.
2. Первый mark price в окне `[entry_due_at, entry_due_at + 10s]` становится входом.
   Если mark нет — наблюдение `unscored`, без импутации. Окно шире шага
   обновления native-снимка рынка (~5.5–6 с): при прежних 5 с примерно каждое
   пятое решение оставалось без входа. Фактическая задержка хранится в
   `entry_at − entry_due_at`, её можно отфильтровать при анализе.
3. Для каждого горизонта `h ∈ {60, 300, 900}`:
   `exit_due_at = decided_at + 1s + h`.
4. Выход — первый mark в окне `[exit_due_at, exit_due_at + 30s]`.
   Если mark нет — закрытие свечи, ближайшее после `exit_due_at` в пределах
   двух интервалов. Если нет и свечи — `unscored`.
5. `move_bps = (exit / entry − 1) × 10 000`, для directional умножается на
   направление сигнала; для absolute берётся модуль.
6. MAE/MFE считаются по mark-точкам пути, которые пишутся не чаще раза в 15 с.
   При разрывах пути они отражают только наблюдённые точки.
7. Покрытие = `scored / observed`; оно показывается рядом с каждой метрикой.

Результат — **gross bps**. Справочный порог издержек (около 9 б.п. round-trip)
не вычитается: это измерение сигнала, а не симулятор исполнения. Mark price
также не является исполнимой ценой; выводы нельзя читать как «доходность
стратегии».

## Контроль

Для каждого эпизода выбираются 5 неактивных инструментов. Метод задаётся
полем `control` контракта.

### `random_scout_vol_5` (flow.continuation v2)

- кандидаты — вся вселенная скаута (~700 инструментов), а не строки скана;
- вне attention-плана: не в `plan.selected` и не в `plan.detail`;
- не сигнальный символ и не тот же базовый актив на другой площадке
  (`BINANCE:BNB` и `BNB` считаются одним активом), и не больше одного
  контроля на базовый актив;
- у кандидата есть mark price в момент решения, иначе вход не оценить;
- по возможности тот же bucket `round(log2(vol) × 2) / 2`, где `vol` —
  скаутская волатильность: RMS скорости изменения mark price (б.п./с) за
  последние ~120 интервалов скаута (~10 минут), минимум 12 интервалов.
  Это та же величина, с которой сравнивает allocator attention v5+;
  у сигнала и у контроля она считается одинаково. Это **не NATR**.

Почему не NATR: в unified-режиме обзорные слоты пересобираются каждый скан
(в среднем 13 из 14 символов новые каждые 5 с). Свечи успевают загрузиться
только для detail-символов, NATR был у ~2 % обзорных строк, и v1 оставляла
контрольные группы пустыми. Скаутская волатильность есть для всей вселенной
без дополнительных запросов к биржам.

Replay-записи скаутскую волатильность не содержат, поэтому в replay контроли
v2 пустые; измерение самого сигнала это не затрагивает.

### `random_natr_5` (остальные контракты v1)

- строки скана того же `window`, кроме сигнального символа и `plan.detail`;
- по возможности тот же bucket `round(log2(NATR) × 2) / 2`.

### Общее

- seed детерминирован от `episode_id`, поэтому выбор воспроизводим;
- если в bucket меньше пяти, поиск расширяется к ближайшим bucket, но подмена
  не скрывается: в `bot_control_sets.bucket` и `symbols` видно, что выбрано.

Контроль проходит те же вход/выход. Для directional контроля движение
умножается на направление наблюдения; для absolute — модуль. Разность
«наблюдение минус среднее контролей» — основной показатель превышения фона.

Контроли совпадают по времени и волатильности, но не по ликвидности и
корреляции. Это остаточное ограничение, а не полное устранение рыночного фона.

## Статистика

Для каждого бота и версии:

- N наблюдений, N оценённых, покрытие.
- Hit rate с Wilson 95% CI (только directional).
- Среднее и медианное движение в б.п. с block bootstrap CI.
- MAE/MFE: медианы.
- Разрез по силе 1–4; `rank 0` исключён, потому что означает отсутствие данных.
- Превышение контроля с CI.
- Разбивка по 1 / 5 / 15 мин; основной — 5 мин.

Главный тест `flow.continuation`:

```
mean signed bps (rank 3–4) − mean signed bps (rank 1–2) > 0
```

Сравнение идёт на 5-мин горизонте. Остальные горизонты, отдельные ранги,
символы и сессии — exploratory. Они показываются, но не называются выводом.

Пороги показа:

| Оценённых наблюдений | Формулировка |
|---:|---|
| 0 наблюдений | нет наблюдений |
| есть наблюдения, 0 оценённых | ожидает исходов |
| 1–29 | мало данных |
| 30–99 | предварительно |
| ≥100 | достаточно данных |

Block bootstrap группирует наблюдения по 15-минутным блокам, потому что
соседние эпизоды зависимы. Если блоков меньше трёх, интервал не строится:
в отчёте будет «мало блоков», а не ложная точность.

Когда все девять ботов реализованы, их главные p-value проходят через
Benjamini–Hochberg с q=0.1. Пока реализован один бот, поправка не меняет
результат; функция `benjamini_hochberg` уже готова. Парные гипотезы
(`formation.hold/break`, `liquidation.continuation/exhaustion`) после
реализации должны опираться на один триггерный эпизод и общий control set;
это требование к их триггерам, текущий прототип его ещё не проверяет.
Поэтому BH для таких пар — приближение, а не точный тест.

## Хранение

Все таблицы живут в существующей SQLite-базе screener:

| Таблица | Смысл |
|---|---|
| `bot_versions` | контракт, версия, хеш |
| `bot_state` | активный эпизод по боту/символу/окну |
| `bot_observations` | одно наблюдение на эпизод; `source=live` или `replay` |
| `bot_outcomes` | исход на каждый горизонт |
| `bot_path_points` | mark-точки для MAE/MFE; удаляются после последнего горизонта |
| `bot_control_sets` | выбранные контроли, bucket, направление |
| `bot_control_points` | вход/выход каждого контроля на горизонт |

Отдельного процесса, второй подписки на биржу и второй базы нет.

## Runtime

- `Screener.scan()` вызывает `BotObservatory.tick()` после обновления
  mark-цен и attention-плана.
- `Screener.run()` вызывает `BotObservatory.settle()` раз в 5 секунд.
- `settle()` сначала пытается закрыть исход по mark, затем по свече,
  затем помечает `unscored`. Не более 8 candle-fallback запросов за проход.
- В demo-режиме наблюдатели не пишут данные.
- `SCALPER_BOTS=0` отключает наблюдателей полностью, не трогая screener.
- Ошибка триггера или отчёта логируется и не ломает screener.

## Telegram

Команды доступны при `--notify` и настроенном Telegram:

```
/bots
```

Краткий список: для каждого бота N, покрытие, главная метрика с интервалом и
статус. Не реализованные боты помечены «ожидает реализации».

```
/bot flow.continuation
```

Полная карточка: гипотеза, наблюдения, покрытие, 5-мин метрика, hit rate,
сила 3–4 против 1–2, разница с CI и p, контроль, MAE/MFE, версия и хеш
контракта.

Команды добавлены в `setMyCommands`. Они не отправляют сигналы на каждое
событие: только отчёт по запросу.

## Live и replay

Это два независимых трека.

- **Live** — единственный источник официальной статистики. Начинается с
  момента запуска и не заполняется задним числом. Агрегаты читают только
  `source='live'`.
- **Replay** — офлайн-прогон по записанному screener-логу. Пишет отдельную
  SQLite-базу с `source='replay'` и не попадает в live-агрегаты.

Причина разделения: backfill ускоряет набор N, но смешивает периоды, условия
отбора и версии контрактов. Быстрая проверка гипотезы не должна выглядеть как
live-подтверждение.

### Что нужно для replay

Нужен JSONL, записанный screener'ом:

```powershell
uv run hyperdata-screener --record .runtime/scan.jsonl
```

В каждой строке должны быть полные `rows`: `snapshot`, `hyperdata`,
`strength`, `analysis_gate`. Один только attention-архив
(`manifest.json` + `scout`/`assignment`) не содержит OFI и native-снимков,
поэтому `flow` по нему воспроизвести нельзя.

Запись attention-плана в лог добавлена в текущую версию, чтобы контрольные
инструменты выбирались так же, как в live. Для старых записей без поля
`attention` контроль может включать инструменты, которые были в плане.

### Запуск

```bash
python -m extensions.scalper.bots.replay .runtime/scan.jsonl --output .runtime/bots-replay-1
python -m extensions.scalper.bots.replay .runtime/scan.jsonl --output .runtime/bots-replay-2 --bot flow.continuation
```

Выходной каталог должен быть новым. Внутри:

```
protocol.json       контракты, версии, хеш входа, ограничения
summary.json        та же статистика, что в /bots, но для source=replay
observations.csv    наблюдения, исходы на 1/5/15 мин, среднее контроля
bots-replay.sqlite  отдельная база; live-журнал не изменяется
```

Replay не обращается к биржам, AI, Telegram или live-БД. Исходы считаются
только по записанным mark-ценам; candle-fallback, комиссии, funding и
проскальзывание не используются. Незакрытые к концу записи исходы помечаются
`unscored`, а не заполняются будущей ценой.

`strength` и `native.direction` берутся из записи, а не пересчитываются
заново. Для проверки новых порогов нужен новый лог или отдельный
версионированный пересчёт триггера.

Для торгового backtest с издержками остаётся отдельный
`scripts/backtest_signals.py`; это другой вопрос и другой контур.

## Порядок запуска

1. `flow.continuation`: журнал, исходы, контроли, `/bots`, `/bot`.
2. `attention.relative_move` + `ai.direction` + `ai.context`.
3. `formation.hold/break` + `liquidation.continuation/exhaustion` + `whale.follow`.
4. `funding.contrarian` с горизонтами 1–4 часа.
5. Разговор о капитале — только после FDR и будущего holdout.

## Ограничения

- Mark price не исполним; результат — наблюдение, не доходность.
- Боты наблюдают только текущий universe screener (attention plan), а не весь
  рынок. `flow.continuation` измеряет поток внутри отобранных инструментов;
  это не глобальный поток по всем парам.
- Издержки не вычитаются; порог 9 б.п. показан справочно.
- Контроль не учитывает ликвидность и корреляцию с сигналом.
- Block bootstrap при короткой истории даёт мало блоков и широкие интервалы.
- Сила фиксируется на входе в эпизод; последующее изменение ранга не
  переписывает наблюдение.
- `rank 1` — фоновый сигнал; он нужен как слабая группа сравнения, а не как
  рекомендация входа.
- Восемь ботов пока не реализованы; их появление требует отдельных
  триггеров и тестов, а не только записи в реестре.
